# Build Brief — DAA Remote Monitoring & Control

**Audience:** Delicate Courier Platform backend + frontend engineers.
**Status:** Greenfield work on top of an existing, shipping-ready WordPress plugin (DAA 0.1.0).
**Read first:** the four attached docs (`README.md`, `INSTALL.md`, `RUNBOOK.md`, `SIM-REPORT.md`) and inspect `delicate-api-adapter-0.1.0.zip`. The plugin works standalone — you're bolting on remote rails, not rewriting it.

---

## 1. Goal in one paragraph

The bakery (Baked by Nataleen) is a non-technical client with no admin access and no staging. The DAA plugin we just built lives in their WordPress install. We need our platform (the .NET API + Next.js frontend) to (a) **see** the moment DAA activates, (b) **mirror in near-real-time** every log entry, decision trace, and configuration state the bakery's plugin has, and (c) **remotely control** every DAA setting (master switch, feature toggles, mapping table, address overrides) without anyone touching the bakery's WP admin. Same pattern needs to work for the next merchant who installs DAA.

**Hybrid sync** is the chosen pattern (push for rare/urgent events, pull for routine high-volume logs). Justification baked into the contract below — don't change the model without re-discussing.

**Full remote control** is requested. That's a meaningful security jump beyond read-only — auth must be tight from day one (token + HMAC signature, audit row for every write, encrypted at rest).

## 3. The contract between the two systems

### 3.1 Identity model

Every DAA install is a **merchant**. A merchant has:

- `slug` — short stable identifier (e.g. `bakedbynataleen`)
- `site_url` — root of their WP install
- `daa_secret` — HMAC key, used by both directions to sign payloads
- `platform_api_token` — bearer token the platform presents to DAA on every pull/control request

Both secrets are **generated platform-side during merchant onboarding** and pasted into the bakery's DAA settings page during install (a new "Remote Monitoring" section we're adding to DAA — see §5).

### 3.2 Auth — both channels

**Defence in depth: token AND signature on every request that mutates state.**

- `X-DAA-Token` HTTP header — bearer token; gates "is this the right caller"
- `X-DAA-Signature` HTTP header — `base64(HMAC_SHA256(daa_secret, raw_request_body))`; gates "is this exact payload one they signed"
- `X-DAA-Actor` HTTP header — set by platform on control requests, identifies the staff user who initiated the action; logged on DAA side for audit

Push direction (DAA → platform) uses the signature only — the token isn't relevant in that direction since the platform doesn't issue itself credentials. Identity is established by `merchant_id` in the envelope, verified by HMAC against the merchant's stored secret.

Pull and control direction (platform → DAA) requires both headers. Token-only or signature-only requests get HTTP 401.

### 3.3 Envelope format (all requests, both directions)

```json
{
  "merchant_id": "bakedbynataleen",
  "schema_version": 1,
  "occurred_at": "2026-05-22T08:14:33Z",
  "request_id": "uuid-v4",
  "payload": { ... }
}
```

`occurred_at` is the originator's clock — platform records this AND its own clock as `received_at` so we can detect skew. `request_id` is a UUID we generate per request, used for idempotency on the receiver.

### 3.4 Push events (DAA → platform)

Endpoint on platform: `POST /api/daa/ingest`

Initial set of events. Each is its own `event` value in the envelope's payload, with `event_data` carrying the specifics:

| event | When fired | event_data |
|---|---|---|
| `plugin.activated` | DAA `register_activation_hook` runs | `daa_version`, `wp_version`, `wc_version`, `php_version`, `dcp_present`, `dcp_version`, `dcp_compatible`, `site_url` |
| `plugin.deactivated` | DAA `register_deactivation_hook` runs | `site_url` |
| `master_switch.toggled` | `update_option_daa_settings` and `master_enabled` differs | `from`, `to`, `actor_user_login` |
| `feature_toggle.toggled` | Same hook, any `*_enabled` key differs | `feature`, `from`, `to`, `actor_user_login` |
| `settings.saved` | Same hook, any non-toggle key differs | `changed_keys[]`, `snapshot` (full new settings, with secrets redacted) |
| `dependency.changed` | DCP presence or version changed since last check | `previous_status`, `current_status` |
| `log.error` | DAA logger writes a row with `level=error` | `log_id`, `feature`, `message`, `context`, `order_id` |

All push calls are fire-and-forget on the DAA side — `wp_remote_post()` with `blocking => false` and a 2-second timeout. The bakery's checkout must NEVER block waiting on us. Push reliability is best-effort; the **pull channel is the source of truth for completeness**.

### 3.5 Pull endpoints (platform → DAA, READ)

Namespace: `delicate-api-adapter/v1` (so URL prefix is `https://bakerysite.tld/wp-json/delicate-api-adapter/v1/...`).

| Method | Path | Returns |
|---|---|---|
| GET | `/heartbeat` | `{ daa_version, time, dcp_compatible, master_enabled }` — tiny, cheap, called frequently |
| GET | `/logs?since_id=N&limit=100&level=info` | log rows with `id > since_id`, ASC, capped to `limit`, optional level filter |
| GET | `/settings` | full settings array, with `daa_secret` and `platform_api_token` replaced by `"***"` |
| GET | `/dependency` | `DAA_Dependency_Check::get_status()` output |
| GET | `/traces?since_id=N&limit=20` | recent `_daa_decision_trace` blobs from orders (queries postmeta or HPOS order meta) |

### 3.6 Control endpoints (platform → DAA, WRITE)

| Method | Path | Body | Effect |
|---|---|---|---|
| POST | `/settings` | full settings array | replaces stored settings (the existing pre-update transforms still run — mapping & overrides get re-JSONified server-side) |
| POST | `/master/on` | `{}` | shortcut: flip master ON |
| POST | `/master/off` | `{}` | shortcut: flip master OFF |
| POST | `/logs/clear` | `{}` | empties `wp_daa_logs` table |
| POST | `/coupon/rotate` | `{ new_code }` | sets `test_mode_coupon` to provided value |

Every successful control request writes a row to DAA's own `wp_daa_logs` with feature `remote_control` and the `X-DAA-Actor` value in context — so the bakery's local log shows everything the platform did, and our platform's audit log shows the same thing from its side.

### 4.3 Ingest endpoint (`POST /api/daa/ingest`)

```csharp
[Route("api/daa/ingest")]
[ApiController]
[AllowAnonymous]                                          // HMAC-gated, not user-auth-gated
public class DaaIngestController : ControllerBase
{
    private readonly IDaaSignatureValidator _sig;
    private readonly DaaMerchantService _merchants;
    private readonly IDaaEventDispatcher _dispatcher;
    private readonly ILogger<DaaIngestController> _log;

    [HttpPost]
    public async Task<IActionResult> Post([FromBody] JsonElement envelope, CancellationToken ct)
    {
        // 1. Look up merchant by envelope.merchant_id (deserialize once, look up, fail-closed on unknown)
        // 2. Read raw body again from HttpContext (Request.Body, after enabling buffering in middleware)
        // 3. Validate X-DAA-Signature against merchant.DaaSecret
        // 4. Idempotency: drop if envelope.request_id already seen (small in-memory LRU is fine, or a unique index on SystemEvents.RequestId)
        // 5. Dispatch to IDaaEventDispatcher — this records the event to SystemEvents + applies any side effects
        //    (e.g. plugin.activated: set merchant.FirstSeenAt; settings.saved: store snapshot in DaaSettingsSnapshot)
        // 6. Always return 200 OK on success; signature failure returns 401 with a dummy body
    }
}
```

Critical: enable HttpContext request-body buffering for this route (`builder.AddControllers().AddJsonOptions(...)` plus `Request.EnableBuffering()` middleware) so the signature validator can re-read the raw bytes after model binding. JSON body deserialization is destructive otherwise.

OpenTelemetry: every ingest call is automatically traced by the existing instrumentation. Add a custom span attribute for `daa.event_name` and `daa.merchant_slug` so traces filter cleanly.

### 4.4 Pull worker (Hangfire recurring job)

```csharp
public class DaaPullSweepJob
{
    private readonly DaaMerchantService _merchants;
    private readonly IDaaRemoteClient _remote;
    private readonly AppDbContext _db;
    private readonly ILogger<DaaPullSweepJob> _log;

    // Registered as a recurring job in Program.cs:
    //   RecurringJob.AddOrUpdate<DaaPullSweepJob>(
    //       "daa-pull-sweep", j => j.RunAsync(CancellationToken.None), "*/30 * * * * *");
    //
    // 30-second cadence sweeps EVERY active merchant. For staff actively watching a
    // tab, the frontend will additionally fire on-demand pulls every 10s while the
    // tab is open (so the live-tab experience is faster without overloading Hangfire).

    public async Task RunAsync(CancellationToken ct)
    {
        var merchants = await _merchants.GetActiveAsync(ct);
        foreach (var m in merchants)
        {
            try
            {
                await PullMerchantAsync(m, ct);
            }
            catch (Exception ex)
            {
                _log.LogWarning(ex, "Pull failed for {Slug}", m.Slug);
                // never throw — one bad merchant must not poison the sweep
            }
        }
    }

    private async Task PullMerchantAsync(DaaMerchant m, CancellationToken ct)
    {
        // 1. Heartbeat (cheap, sets LastSeenAt regardless of other outcomes)
        // 2. /logs?since_id=<max(remote_id) for this merchant>&limit=500 → bulk insert
        // 3. /settings → diff against latest snapshot; if changed, insert a new DaaSettingsSnapshot
        // 4. /dependency → if changed since previous, fire a synthetic system event "dependency.observed-change"
        // 5. /traces?since_id=<max(order_id) for this merchant>&limit=20 → bulk insert
    }
}
```

The 30s background sweep + 10s frontend-driven foreground polls give you the "real-time" feel staff want, without persistent SSE/WebSocket infrastructure.

If you DO want to push live logs into an open browser tab (rather than the frontend polling our API every 10s), the cheapest path is to add a tiny SignalR hub later — defer that to v2.

### 4.6 Outbound HTTP client

```csharp
public interface IDaaRemoteClient
{
    Task<HttpResponseMessage> SendAsync(
        DaaMerchant merchant,
        HttpMethod method,
        string relativePath,
        object? body,
        long actorUserId,
        CancellationToken ct);
}
```

Implementation responsibilities:
- Compose URL: `merchant.SiteUrl + "/wp-json/delicate-api-adapter/v1" + relativePath`
- Serialize body to JSON
- Compute HMAC signature of body bytes
- Set `X-DAA-Token`, `X-DAA-Signature`, `X-DAA-Actor` headers
- Send via `HttpClient` (registered in DI with `AddHttpClient<IDaaRemoteClient, DaaRemoteClient>()`, which gives you the OpenTelemetry HttpClient instrumentation automatically)
- Persist a `DaaRemoteAction` row regardless of outcome
- 10-second timeout per call

Register a named/typed client so the existing OTel HttpClient instrumentation traces every outbound call to the bakery's WP. Set a custom request property `daa.merchant.slug` for trace filtering.

### 4.8 Secrets handling

`DaaMerchant.DaaSecretEncrypted` and `PlatformApiTokenEncrypted` use ASP.NET Core's `IDataProtector` (with a key-ring per environment). NEVER log either value. NEVER round-trip them through the admin UI — when a staff member opens a merchant, the secrets are displayed as `••• click to reveal` and revealing requires re-authentication if your existing patterns support it.

Onboarding flow:
1. Staff creates a new merchant in admin: name, site URL → platform generates both secrets, stores encrypted, returns them ONCE in the response
2. Staff pastes the two secrets into the bakery's DAA settings page (the new "Remote Monitoring" section described in §5.1)
3. Bakery clicks Save — DAA writes them locally and the first `settings.saved` push fires
4. Platform receives the push, validates signature against the stored secret → merchant.Status transitions Pending → Active

If a secret leaks: regenerate platform-side, re-paste into DAA. Old secret invalidates immediately (in-memory rotation, no DB cache).

## 5. DAA-side build (additions to the existing plugin)

The current DAA 0.1.0 ships from `delicate-api-adapter-0.1.0.zip`. These additions follow the established `DAA_Feature` pattern. **No changes to existing classes' public behaviour are required**; existing tests remain green.

### 5.1 Settings additions (`includes/class-daa-settings.php`)

Add new keys to `defaults()`:

```php
'remote_monitoring_enabled' => '0',
'merchant_id'               => '',
'platform_ingest_url'       => 'https://api2.delicatecourier.co.za/api/daa/ingest',
'platform_api_token'        => '',
'daa_secret'                => '',
```

Render them in a new settings section "Remote Monitoring", placed at the bottom of the settings page. The two secret fields use `type="password"`. On save:
- If a password field's submitted value is the literal `***`, KEEP the stored value (the "leave blank to keep existing" pattern)
- Otherwise store as given

Mark `daa_secret` and `platform_api_token` so that `GET /settings` (the pull endpoint, §3.5) ALWAYS replaces them with `"***"` in the response payload.

### 5.2 New class: `DAA_Remote_Push`

File: `includes/class-daa-remote-push.php`. Extends `DAA_Feature`. Slug: `remote_push`.

Hooks:
- `update_option_daa_settings` (3 args: `$old`, `$new`, `$option`) — diff and emit `master_switch.toggled`, `feature_toggle.toggled`, `settings.saved` as appropriate
- A new internal action `daa_log_written` fired by `DAA_Logger::log()` when level is `error` — emits `log.error` event
- DCP dependency state cached per-request via `DAA_Dependency_Check::get_status()`; the push class re-checks at the END of every request via `shutdown` hook and emits `dependency.changed` if it differs from a persisted snapshot
- Plugin activation/deactivation pushes are fired DIRECTLY from `DAA_Plugin::activate()` and `::deactivate()` (not via a hook — they need to fire even if the plugin's hook isn't registered yet)

Outbound mechanism: `wp_remote_post(url, [ 'body' => $json, 'headers' => [...], 'timeout' => 2, 'blocking' => false ])`. The `blocking => false` ensures checkout never waits on a slow platform.

Signing helper: a new tiny class `DAA_Sig` with two static methods — `sign(string $body, string $secret): string` and `verify(string $body, string $signature, string $secret): bool`. Algorithm: `base64_encode(hash_hmac('sha256', $body, $secret, true))`.

### 5.3 New class: `DAA_Remote_API`

File: `includes/class-daa-remote-api.php`. Extends `DAA_Feature`. Slug: `remote_api`.

Registers REST routes on `rest_api_init`:

```php
register_rest_route( 'delicate-api-adapter/v1', '/heartbeat', [
    'methods'             => 'GET',
    'callback'            => [ $this, 'heartbeat' ],
    'permission_callback' => [ $this, 'authorize' ],
] );
// ... etc for logs, settings, dependency, traces, settings POST, master/on, master/off,
//     logs/clear, coupon/rotate
```

`authorize()`:
1. Pull `X-DAA-Token` from `$request->get_header( 'x_daa_token' )` (WP lowercases + underscores)
2. Compare in constant time (`hash_equals`) to stored `platform_api_token`. Fail → return `WP_Error` with 401.
3. For POST/PUT/DELETE: pull `X-DAA-Signature`, recompute against the raw body (`$request->get_body()`), compare in constant time. Fail → 401.
4. Optionally read `X-DAA-Actor`, pass through to the endpoint via a request attribute for audit logging.

For all WRITE endpoints, after the work is done, write a row to `wp_daa_logs` via `DAA_Logger::info( 'remote_control', "Remote action: $action", [ 'actor' => $actor, 'request_id' => $request_id ] )`.

### 5.5 Backward compatibility

If `remote_monitoring_enabled` is `'0'` (the default), `DAA_Remote_Push` and `DAA_Remote_API` are no-ops. They register no outbound calls, the REST endpoints exist but return 401 immediately on the empty token. This means an existing bakery install that updates from 0.1.0 to 0.2.0 sees no behaviour change until they explicitly enable remote monitoring and paste credentials.

## 7. Non-negotiables for the dev team

These are the load-bearing properties — if any is broken in implementation, the integration is dangerous in production:

1. **Bakery's checkout never blocks on us**: all outbound push calls from DAA use `blocking => false`. Verified in code review on every `wp_remote_post`/`wp_remote_request` call DAA makes.
2. **Every remote control call is logged on BOTH sides**: DAA writes a `remote_control` row, platform writes a `DaaRemoteAction` row. A change on the bakery's site that ONLY exists in our audit log is a security incident.
3. **Tokens/secrets never appear in logs, responses, or admin UI without explicit reveal**: this applies to OpenTelemetry traces too — make sure you scrub `X-DAA-Token` and `X-DAA-Signature` from the OTel HttpClient instrumentation's captured headers.
4. **HMAC verification uses constant-time comparison** (`hash_equals` on PHP side, `CryptographicOperations.FixedTimeEquals` on .NET side).
5. **Idempotent ingest**: a duplicate `request_id` is dropped silently with 200, not double-processed. This protects against DAA's fire-and-forget retries-on-network-flake.
6. **Hangfire job for the sweep never throws upward**: one bad merchant must not stop the sweep for all others. Per-merchant try/catch, log to OTel, continue.
7. **DCP integration is not affected**: nothing in this work touches DCP. Verify by running through the existing six-scenario simulation matrix (see `SIM-REPORT.md`) on the bakery's staging WP after DAA 0.2.0 is installed — all six scenarios must still pass.
