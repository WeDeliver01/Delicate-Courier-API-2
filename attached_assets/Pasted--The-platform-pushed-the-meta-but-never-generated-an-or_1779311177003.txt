. The platform pushed the meta but never generated an order note for it
Looking at the plugin code, there is no add_order_note anywhere in the write-back path (dcp_rest_receive_shipment_meta, lines 489-583). Order notes are only added by dcp_sync_order on the outbound order push. So even when meta is written successfully, no customer-visible note will ever be created by the plugin. If your v2.2.6 changelog promised "customer-visible note with the tracking number" on shipment booking, that promise lives on the platform side, and is presumably done via a separate WC REST API call (the WC REST API is the only WP-facing surface that can create order notes from outside; the plugin's own /shipment-meta endpoint doesn't create them). That separate call is where CK/CS would matter.
To confirm: look at the platform's tracking pushback code. There are likely two calls: (a) signed POST to /shipment-meta for the meta keys, and (b) authenticated POST to wc/v3/orders/{id}/notes for the order note. If (b) is failing silently because CK/CS are wrong, that explains the missing note even though (a) succeeds.
3. _dcp_tracking_number is being sent under a different key name
The plugin's whitelist (line 553) accepts only keys starting with _dcp_. If the platform sends tracking_number (no prefix) or _dcp_waybill or _dcp_tracking_no (different name), the plugin silently puts it in the skipped list and the metabox keeps showing "Awaiting waybill" since it specifically reads _dcp_tracking_number. The platform's success message "Pushed 9 shipment meta key(s)" doesn't tell you how many were actually accepted vs skipped — only how many were sent.
To confirm: go to the plugin settings page, open the debug log, and look for meta.recv entries. The line format is order=11990 updated=N skipped=M keys=a,b,c,.... If updated < 9 and skipped is non-empty, you've found a key-name mismatch. If keys= doesn't include _dcp_tracking_number, the platform isn't sending it.
4. _dcp_tracking_number is being sent but as null
Line 557-558 of the plugin stores null as empty string ''. The metabox at line 2044 treats empty as "Awaiting waybill". So if the platform is sending the key but the value is null (because it hasn't been populated yet from Shiplogic), the result is exactly what you're seeing: green success message, status visible, tracking blank. This is essentially cause #1 explained at the database level.
To confirm: the debug log will show keys= including _dcp_tracking_number but updated count will be 9 (it counts writes regardless of value). To see the value, you'd need to peek at the order meta directly (e.g. in a Tools → "View order meta" plugin, or via wp post meta list ORDER_ID over WP-CLI) — if the key is there with an empty value, this is cause #4.
5. Webhook secret mismatch between plugin and platform
If the secret didn't match, the plugin would return 401 before writing anything, and the platform would log a failure rather than "Pushed 9 keys". So this is ruled out by the green success message — but worth flagging because it's the failure mode that would feel like a CK/CS mismatch (silent, auth-related). The v2.2.1 fix specifically addressed a sanitize_text_field bug that stripped characters from the secret; if the platform stored the secret using a different sanitiser, signing would still mismatch silently from its side. Verify the two ends hold the same SHA-256 fingerprint of the secret using the v2.2.2 diagnostic.
6. The webhook secret was rotated on one side only
Same effect as #5: a 401 on plugin's side, success on platform's side only if it's not parsing 401 as failure. Less likely given a green message, but worth checking if the secret was changed at any point.
7. The platform writes via WC REST API and CK/CS are wrong
Your original hunch. This is possible only if the platform actually uses that path for something — most likely for the order note rather than the meta keys (cause #2). The plugin itself doesn't help here because it's not the code making the call. If you can check the platform's tracking-push code path, look for an HTTP call to /wp-json/wc/v3/orders/{id} or /notes. If it's there and credentials are stale, the call returns 401 but the platform logs it as success because the meta push (which is the previous step) succeeded.
8. HPOS / legacy table mismatch
The plugin declares HPOS compatibility, but if the site has HPOS enabled and the platform's WC REST API call (cause #7) targets the legacy wp_postmeta table directly, writes would land in a place the metabox doesn't read from. Highly site-dependent. Easy to rule out by confirming whether HPOS is on in WooCommerce → Settings → Advanced → Features.
9. Caching plugin or object cache holding stale order data
The plugin calls $order->save() which invalidates WC's own caches, but a heavy object-cache layer (Redis with stale TTLs, or a host-level page cache that caches the admin) could serve a stale metabox render. Rare and easy to test: hard-refresh the order page, or open it in an incognito window logged in as admin.
